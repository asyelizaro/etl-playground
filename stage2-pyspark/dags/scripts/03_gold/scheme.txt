RELATIONSHIP OVERVIEW
---------------------

artist --< album --< track >-- genre
                       |
                       +---< playlist_track_link >--- playlist
                       |
                       +---< invoice_track_link >--- invoice -- customer
                                                               |
employee -------------------------------------------------------+
         (customer.SupportRepId)

The invoice-to-customer relationship is customer_invoice_link. The diagram
shows the same relationship in a readable direction.

Example path for sales by artist:
  invoice_hub
    -> invoice_track_link + invoice_line_sat (line price and quantity)
    -> track_hub
    -> album_track_link
    -> album_hub
    -> artist_album_link
    -> artist_hub + artist_sat

Track genre is reached through genre_track_link and genre_sat.


NOTES / MODELLING DECISIONS
---------------------------

1. invoice_line is currently represented as a LINK between invoice and track,
   with unit_price and quantity in its LINK SAT. This matches the Silver
   configuration and current Gold joins. The source also has InvoiceLineId:
   if the same track can occur more than once on one invoice, InvoiceId + TrackId
   is not a unique line key. In that case, add an invoice_line_hub keyed by
   InvoiceLineId and link it to invoice_hub and track_hub, or include
   InvoiceLineId in the line-level relationship key.

2. employee.reports_to is a self-reference. For full relationship history,
   model it as employee_manager_link (employee_hk, manager_employee_hk);
   currently it is kept as an attribute in employee_sat.

3. track.MediaTypeId is present in the source, but media_type is not in the
   current ingestion table list. Add media_type_hub, media_type_sat, and a
   media_type_track_link only if that source table is added to ingestion.

4. playlist_track has only the two relationship keys in this source. A separate
   playlist_track_sat is unnecessary unless the source gains descriptive
   attributes for that relationship.

5. CustomerId is carried by invoice as well as represented in
   customer_invoice_link. This is intentional in the current Silver setup; the
   LINK is the canonical relationship for joins, while source foreign keys
   provide the relationship input.
